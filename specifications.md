# Thirty — Specifications

**Product:** Thirty — an AI-native CRM and business operations platform for service SMBs
**Source PRD:** [references/PRD.md](references/PRD.md) (PRD v2.0, "AI-Native CRM and Business Operations Platform for SMBs")
**Document purpose:** Defines exactly what this repository builds: a working MVP that demonstrates the PRD's core thesis end-to-end. The PRD describes an 18-month, multi-team product; this specification scopes the first buildable increment (the "walking skeleton" of the Minimum Lovable Product, PRD §52) that a founder can run, demo, and iterate on.

---

## 1. Product summary

Thirty is one system that owns the complete customer lifecycle for a service business:

**Lead → Opportunity → Quote → Project → Invoice / Payment → Support Ticket → Retention**

Its defining property (PRD Final Recommendation): sales, delivery, money, and support are not separate modules — they are related states in one business context that humans and AI agents operate together, with every action attributed, auditable, and policy-controlled.

### What the MVP demonstrates

1. **One customer context** — a person/company record shows every deal, project, invoice, payment, and ticket on a single chronological timeline (PRD CORE-03).
2. **Lead-to-cash flow** — capture a lead, qualify it, move it through a pipeline, generate a quote, win the deal, auto-create the delivery project, invoice it, record payment (PRD §15.2, §15.3, SAL-01, OPS-01, FIN-01).
3. **Policy-controlled agents** — five agents (Owner Chief of Staff, Intake, Sales, Delivery Coordinator, Support) that observe, recommend, and execute according to autonomy tiers, with every run recording evidence, actions, and cost, and Tier-1+ external actions gated behind a human approval queue (PRD §21, §22, AGT-01, AGT-02).
4. **Automations with safety rails** — trigger/condition/action rules with simulation mode, versioning, enable/pause, and a per-run execution log (PRD AUT-01..03, §28).
5. **Ask Business** — a natural-language query box that answers cross-module questions with source records and confidence (PRD §20, AI-01). Works fully offline via a deterministic query engine; optionally uses the Anthropic API when a key is configured.
6. **Auditability** — every write (human, agent, automation, API) lands in one queryable audit log with actor, before/after, and timestamp (PRD §42, ADM-01).
7. **Owner Command Centre** — a home dashboard answering "what changed, what's at risk, what needs me" (PRD §14).
8. **REST API + lead capture endpoint** — versioned JSON API over core objects and a public form-ingestion endpoint (PRD INT-03 subset).
9. **Custom fields** — admins can add typed custom fields to core objects without code (PRD CORE-01 subset).

### Explicitly out of scope for this MVP

Deferred, consistent with PRD §54 non-goals plus practical MVP cuts: multi-tenant auth/SSO, real email/calendar sync, external integrations (Stripe/Xero/Google — modeled as connection stubs only), MCP server, visual drag-and-drop workflow canvas (a structured builder ships instead), client portal, knowledge base, marketplace/App SDK, embeddings/semantic search, native mobile, payments processing, accounting ledger, i18n.

## 2. Target user & primary journeys

Persona set per PRD §10, collapsed for MVP into a single "Owner/operator" user (no login; single-workspace demo). Journeys the MVP must support:

- **J1 Guided demo setup:** the seeded workspace represents a small consultancy with realistic data across all modules, so the product is explorable in minutes (PRD §15.1 substitute).
- **J2 Lead to cash:** create/capture lead → qualify → pipeline stages → quote → mark won → project auto-created → invoice → payment recorded → dashboard reflects it.
- **J3 Sale to delivery:** won deal produces a project with scope, value, contact, milestones, and tasks carried over.
- **J4 Support to retention:** create ticket (manually or via API) → agent triages, drafts reply → human approves → resolution updates customer health.
- **J5 Create an automation:** pick a template or compose trigger/conditions/actions → simulate against live data (no side effects) → publish → watch run history.
- **J6 Ask the business:** type "which invoices are overdue?" → answer with linked source records, confidence, and freshness timestamp.

## 3. Functional specification

### 3.1 Modules & navigation

Sidebar navigation (PRD §14, subset): **Home, Customers, Sales, Delivery, Money, Support, Automations, Agents, Ask, Analytics, Audit, Settings**.

### 3.2 Home — Owner Command Centre

Panels: daily briefing (generated by Chief of Staff agent), pipeline & cash snapshot, at-risk deals (stale > N days), overdue invoices, delivery exceptions (overdue tasks/milestones), open ticket escalations, pending agent approvals, recent automation failures, recommended actions. Every number links to the filtered list behind it.

### 3.3 Customers

- **People** and **Companies** with standard fields + custom fields; person↔company linkage with role.
- Record page: header (health badge, tags, key facts), **unified timeline** (notes, stage changes, quotes, invoices, payments, tickets, agent actions — chronological, filterable by type), related records (deals, projects, invoices, tickets).
- Notes can be added from the record page.
- Duplicate detection on create (same email / same normalized name) with a warning (CORE-04 lite).
- **Customer health**: computed score (recent activity, overdue invoices, open escalated tickets, project overruns) shown as Good / Watch / At-risk.

### 3.4 Sales

- Single configurable **pipeline** with ordered stages (default: New → Qualified → Proposal → Negotiation → Won / Lost).
- **Deals** (covers lead + opportunity): name, company/person, value, stage, priority, source, owner, expected close, notes.
- **Kanban board** with stage move (buttons/dropdown; drag optional) + table view.
- Stage changes append to timeline and emit events (automation triggers).
- **Won** requires/creates handoff: project auto-created from deal (J3). **Lost** captures a reason.
- Lead capture: `POST /api/v1/forms/lead` (public) creates a deal + person, tagged with source; Intake agent enriches/classifies it.

### 3.5 Delivery

- **Projects**: name, customer, linked deal, status (Planning / Active / On hold / Done), start/due dates, value.
- **Milestones** (name, due, status) and **Tasks** (title, assignee, due, status, milestone link).
- Project page shows progress (task completion %), overdue flags, and timeline.
- Overdue milestone/task events feed dashboard "delivery exceptions" and the Delivery Coordinator agent.

### 3.6 Money

- **Products/services catalogue** (name, unit price).
- **Quotes**: line items, totals, status (Draft / Sent / Accepted / Rejected); acceptance can flip the linked deal to Won.
- **Invoices**: line items, issue/due dates, status (Draft / Sent / Paid / Overdue / Void); can be generated from a quote or project.
- **Payments** recorded against invoices; partial payments supported; invoice auto-marks Paid when balance reaches zero.
- Overdue detection (due date passed, unpaid) drives reminders (automation template) and dashboard cash panel.

### 3.7 Support

- **Tickets**: subject, customer, priority (Low/Normal/High/Urgent), category, status (Open / Pending / Resolved / Closed), SLA due (from priority), assignee.
- Ticket page: message thread (customer + internal notes), AI triage summary + suggested response (Support agent), escalation flag.
- Resolution/reopen events update customer health.

### 3.8 Automations

- Definition = **trigger** (event type, e.g. `deal.stage_changed`, `invoice.overdue`, `ticket.created`, `deal.created`) + **conditions** (field comparisons on the event payload/record) + **actions** (create task, update field, add tag, add note, create ticket, send message *(logged, not actually emailed)*, request approval, run agent).
- Structured builder UI (form-based; each automation renders as a readable trigger→condition→action card).
- **Templates** shipped: lead response task, deal-won → project kickoff checklist, invoice overdue reminder, ticket escalation.
- **Simulation mode**: run against a matching historical/live record, log what *would* happen, zero writes (AUT-02, NFR "no external side effects in test mode").
- **Versioning**: publishing snapshots an immutable version; runs record the version used; pause/resume; per-run step log with status and errors (AUT-03).

### 3.9 Agents

Five seeded agents (PRD §52) with **autonomy tiers** (PRD §22):

| Agent | Function (MVP) | Default tier |
| --- | --- | --- |
| Owner Chief of Staff | Generates the daily briefing: what changed, risks, priorities, recommended actions | 0 Observe |
| Intake & Enrichment | On new lead: dedupe check, classify priority/source quality, route (assign + task) | 2 Internal execute |
| Sales | Flags stale deals, drafts follow-ups, recommends next actions per deal | 1 Recommend (drafts need approval to "send") |
| Delivery Coordinator | Watches due dates, flags at-risk milestones, creates catch-up tasks | 2 Internal execute |
| Support | Triages new tickets (priority/category/SLA), drafts responses, escalates | 1 for outbound drafts; 2 for triage fields |

- **Agent runs** record: trigger, evidence (records consulted, with links), reasoning summary, proposed/executed actions, cost estimate (simulated $ figure per PRD transparent-economics), duration, status (AGT-01).
- **Approvals queue**: any action above the agent's autonomous tier (external sends, Tier-1 drafts) becomes a pending approval with a diff/preview; human approves or rejects; both outcomes logged.
- **Policies** per agent: enabled/disabled, tier cap, max actions per day (budget), editable in Agents UI (AGT-02 subset).
- Agent logic is **deterministic/heuristic** in the MVP (rules over live data — honest, testable, offline). When `ANTHROPIC_API_KEY` is set, briefing narrative and ticket/follow-up drafts upgrade to LLM-generated via a small model-gateway module (provider-swappable, per PRD §23) — the action/approval machinery is identical in both modes.

### 3.10 Ask Business

- Global "Ask" page + command-bar entry point.
- **Offline engine**: intent matching over a catalogue of supported questions (overdue invoices, pipeline value by stage, deals likely to slip, customers with open tickets & overdue work, revenue collected this month, top lead sources, at-risk customers, today's priorities…). Each answer returns: text summary, source records (linked), confidence, and data-freshness timestamp (AI-01).
- **LLM mode** (optional key): the question plus a compact structured business snapshot go to the model; the answer must cite the record IDs it used; UI renders the same evidence layout.
- Unsupported questions degrade gracefully with suggestions of what can be asked.

### 3.11 Analytics

Dashboard of operational metrics computed live from the operational store (PRD §51): leads created (30d), pipeline value by stage, win rate, booked revenue, invoiced vs collected vs overdue, delivery on-time rate, open tickets by priority, SLA compliance, automation success rate, agent actions (proposed/approved/executed), estimated AI spend. Simple charts (SVG, no heavy chart deps).

### 3.12 Audit

- Every write goes through the data layer, which records: actor (user / agent:<id> / automation:<id> / api), action, entity type + id, before/after JSON, timestamp, and correlation id (AGT/AUT run id where applicable) (PRD §42).
- Audit page: filterable table (actor type, entity, date), row expands to show the diff.

### 3.13 Settings

- Workspace name; pipeline stage editor; custom field definitions (add/remove typed fields — text, number, date, select — on Person, Company, Deal, Project); agent policies; AI provider key status (env-based, read-only display); data export (JSON download of all core objects — ADM-02 lite); demo data reset.

### 3.14 REST API (v1)

`/api/v1/…`, JSON, no auth in MVP (single-user local demo; header `X-Api-Key` scaffolded for future):

- CRUD: `people`, `companies`, `deals`, `projects`, `tasks`, `quotes`, `invoices`, `payments`, `tickets`
- `POST /api/v1/forms/lead` — public lead capture (name, email, company, message, source)
- `GET /api/v1/audit` — audit query
- `GET /api/v1/ask?q=` — Ask Business
- All writes emit the same events and audit entries as the UI.

## 4. Technical specification

### 4.1 Stack

| Layer | Choice | Rationale |
| --- | --- | --- |
| Framework | **Next.js 15 (App Router) + TypeScript + React 19** | Single deployable modular monolith (PRD §44); server components + server actions keep the data layer server-side |
| Styling | **Tailwind CSS v4** | Fast, consistent UI without a component-library dependency |
| Database | **SQLite** via **better-sqlite3** + **Drizzle ORM** | Zero-infrastructure local system of record; the schema is written portable-relational so it can be migrated to Postgres (the PRD's production choice) later |
| Events | In-process synchronous event bus writing to an `events` table | At-least-once semantics + replayable log (PRD §46 event layer, scaled to MVP) |
| AI | `src/lib/ai/gateway.ts` — provider-agnostic interface; deterministic heuristic provider (default) + Anthropic provider (env key) | PRD §23 model gateway, honest offline fallback |
| Tests | Vitest for engine-level units (automation engine, agent rules, ask engine, money math) | Protects the load-bearing business logic |

### 4.2 Architecture

```
src/
  app/                    # Next.js routes (UI pages + /api/v1)
  lib/
    db/                   # drizzle schema, client, migrations, seed
    core/                 # data-access services (one per module) — ALL writes flow here
    audit.ts              # audit writer (called by core services)
    events.ts             # event bus: emit → persist → dispatch to automations + agents
    automations/          # engine: trigger match, condition eval, action exec, simulation
    agents/               # 5 agents + runner + approvals
    ai/                   # gateway + providers (heuristic, anthropic)
    ask/                  # question catalogue + offline answer engine
    analytics.ts          # metric queries
```

Key invariants:

1. **No route or component touches the DB directly** — everything goes through `lib/core/*` services, which is what makes uniform audit + events possible.
2. **Agents and automations use the same core services as humans** (PRD §18.3: "agents use typed tools and normal business APIs"); an agent cannot write anything the service layer wouldn't allow, and every write carries its actor identity.
3. **Simulation never writes** — the automation engine takes an `execute: boolean`; action handlers return described-effects in both modes and only persist when executing.
4. **Events are facts** — emitted after successful commit, stored in `events`, then dispatched; automation/agent failures never roll back the originating business write.

### 4.3 Data model (principal tables)

`workspace`, `users`, `companies`, `people`, `custom_field_defs`, `pipelines`, `stages`, `deals`, `projects`, `milestones`, `tasks`, `products`, `quotes`, `quote_items`, `invoices`, `invoice_items`, `payments`, `tickets`, `ticket_messages`, `notes`, `tags` (+ join), `automations`, `automation_versions`, `automation_runs`, `agents`, `agent_runs`, `approvals`, `events`, `audit_log`, `settings`.

Conventions: integer autoincrement PKs, ISO-8601 UTC text timestamps, `custom` JSON column on customizable objects, money stored as integer cents.

### 4.4 Non-functional targets (MVP interpretation of PRD §47)

- All writes attributable to an actor: **100%, enforced structurally** (single write path).
- Simulation produces zero side effects: enforced + unit-tested.
- List views render from indexed queries; seed dataset ~150 records loads instantly.
- Accessible semantics: real buttons/links/labels, keyboard-usable forms.
- Deterministic offline operation: no network calls unless an API key is explicitly configured.

## 5. Acceptance criteria (MVP definition of done)

1. `npm run dev` starts the app with seeded demo data; every nav section renders with real data.
2. J2 lead-to-cash can be completed entirely in the UI, and each step appears on the customer timeline and in the audit log with the correct actor.
3. Winning a deal creates a linked project; the handoff carries name, value, customer, and kickoff tasks.
4. An invoice past its due date shows as Overdue on Money, Home, and the customer record; recording full payment flips it to Paid.
5. Creating a ticket produces a Support-agent triage run with evidence and a suggested response requiring approval; approving posts the reply to the thread and logs it.
6. A new lead (UI or `POST /api/v1/forms/lead`) produces an Intake-agent run that classifies and routes it.
7. An automation simulated against historical data logs predicted actions and writes nothing; the same automation published and triggered writes its actions and a run record.
8. Ask Business answers at least 10 distinct question types with linked source records, confidence, and freshness — with no API key configured.
9. The audit page shows human, agent, automation, and API writes distinguishably, with before/after diffs.
10. Engine unit tests (automation matching/conditions/simulation, agent triage rules, money totals/overdue, ask engine) pass via `npm test`.
